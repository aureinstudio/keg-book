## Problem Statement

코리아교육그룹이 출판하는 **교재**에 대해, 바이럴·콘텐츠 마케팅용 글을 한 곳에서 작성·예약하고 **구글 블로그(Blogger)**·**네이버 블로그**로 반영하고, 같은 원고에서 **인스타그램·Threads**용 문안을 만들어 **[Buffer](https://buffer.com/)** 로 예약·게시 큐에 넣으며, **이메일 뉴스레터**는 **[메일리](https://maily.so/)** [개발자 API](https://maily.so/app/guides/dev/dev-api)(`https://api.maily.so`, Bearer 인증)로 발송·연동하고, **카드뉴스** 슬라이드 이미지는 **[Google Gemini API](https://ai.google.dev/gemini-api/docs)** 로 생성하는 흐름을 `keg-book`에서 구축한다. 브랜드·톤·합법 표현 맥락은 `.agents/product-marketing-context.md`를 따른다.

## What Makes This Cool

- 멀티 채널 **단일 편집기** + 발행 큐(예약, 실패 재시도, 로그).
- Blogger는 **공식 API**로 진짜 원클릭 발행.
- 네이버는 정책 한계 안에서 **현실적인 보조**(미리보기·HTML 복사·체크리스트)까지 포함하면 "불가능을 알면서도 쓸모 있다"는 완성도.
- **인스타그램·Threads**는 [Buffer의 인스타·Threads 스케줄링](https://buffer.com/instagram) · [Threads 안내](https://buffer.com/threads)처럼 **제품 내 예약**이 가능하고, keg-book에서는 [Buffer GraphQL API](https://developers.buffer.com/)로 **원고 → 큐 적재**까지 자동화할 수 있다(채널 연결·API 키·플랜 전제).
- **뉴스레터**는 Buffer가 아니라 **메일리**로 자동 발송·연동; keg-book은 HTML·제목 산출, 메일리 API로 구독자·그룹·자동 이메일 트리거 등(도움말 스펙 범위 내)만 담당한다.
- **카드뉴스**는 `_template/card-news/` 스펙·레퍼런스와 원고·프롬프트를 바탕으로 **Gemini API**에서 이미지를 생성한다. **생성 파일·프롬프트 로그·보내기**는 루트 **`_output/card-news/`** (및 필요 시 `_output/shared/`)에 매체별 규칙대로 저장한다. Buffer 업로드 또는 수동 다운로드로 이어지게 한다(모델·이미지 API 세부는 [Gemini 문서](https://ai.google.dev/gemini-api/docs) 기준으로 구현 시점에 확정). 폴더 맵은 `_output/README.md`.

## Constraints

- 작업 범위: **`c:\Users\Admin\Desktop\KEG\keg-book` 만** (다른 레포 수정 없음).
- 네이버: 과거 공지 기준 **블로그 글쓰기용 공식 API는 종료**된 이력이 있음 → "완전 공식 API 자동 발행"을 전제로 하면 리스크 큼.
- 구글: OAuth 2.0 + Blogger API v3 (스코프 `https://www.googleapis.com/auth/blogger`).
- 인스타그램·Threads: **Buffer** 연동 시 [GraphQL API](https://developers.buffer.com/)로 `createPost`(큐 추가·즉시 공유 등) 가능. 인스타는 **비즈니스 계정·미디어 요건** 등 Buffer/Meta 조건을 따른다. ([Threads + Buffer 도움말](https://support.buffer.com/article/857-using-threads-with-buffer))
- 뉴스레터: **Buffer로는 구독자 메일 발송 불가** — [메일리 API](https://maily.so/app/guides/dev/dev-api)로 구현한다(웹훅 등은 메일리 플랜·도움말 기준).
- 카드뉴스: **Gemini API**는 **서버 측**에서만 호출하고, API 키는 클라이언트에 노출하지 않는다. 생성 이미지의 **안전 필터·약관·표시광고** 준수는 제품 책임으로 문서·UI에 남긴다.

## Premises

1. **Blogger 자동 발행은 공식 경로로 MVP에 포함 가능**하다 — agree 권장.
2. **네이버는 MVP에서 (A) 보조 워크플로 또는 (B) 브라우저 자동화** 중 하나를 택해야 하며, (B)는 ToS·계정·차단 리스크를 문서·UI에 명시해야 한다 — agree 권장.
3. 토큰·리프레시 토큰·**Buffer·메일리·Gemini API 키**는 **서버 비밀**로만 보관하고, 로그에 본문·토큰·키를 남기지 않는다 — agree 필수.

## Landscape (요약)

- **Blogger:** API v3로 초안 작성·게시·예약 게시 등 공식 지원. 배포·OAuth만 잘 잡으면 안정적.
- **네이버 블로그:** 업계 공지상 **API 기반 자동 글쓰기 종료** 이력이 있어, "완전 자동" 마케팅은 피하고 대안을 제품 전면에 둔다.

## Approaches Considered

### Approach A: 하이브리드 (권장)

- Blogger: `posts.insert` → `posts.publish` (또는 예약 파라미터 활용).
- 네이버: 에디터에 붙여넣기 좋은 **HTML/Markdown 미리보기**, 이미지는 사용자 업로드 가이드, 또는 **수동 한 번 클릭** 체크리스트.
- 장점: 약관·계정 리스크 최소, 설명 가능한 제품 스토리.
- 단점: 네이버는 "완전 무인"이 아님.

### Approach B: 네이버 브라우저 자동화

- Playwright 등으로 스마트에디터 DOM 조작.
- 장점: 무인에 가까움.
- 단점: UI 변경에 취약, 위반 시 계정 제재 가능성, 유지보수 지옥.

### Approach C: 큐·편집기만 먼저

- 저장소·태그·예약 큐만 구현, 커넥터는 목(Mock).
- 장점: 빠른 시연.
- 단점: 실사용 가치는 한쪽만 연결될 때까지 제한적.

## Recommended Approach

**Approach A (하이브리드)** 로 MVP를 정의하고, README·온보딩에 네이버 한계를 한 줄로 고정한다. 네이버 완전 자동이 하드 요구이면 Phase 2에서 Approach B를 **별도 "실험 모드"**로 격리(기본 비활성 + 경고).

## 설정 UI (API·계정 정보 입력)

**방향: 좋다.** 웹앱이면 “연결 상태·재연결·테스트 발행”을 화면에서 다루는 편이 사용성과 온보딩에 유리하다. 다만 **입력 가능한 것의 종류**를 나눈다.

| 구분 | UI에서 다루는 방식 | 비고 |
|------|-------------------|------|
| **Google / Blogger** | **OAuth 연결** 버튼 → 동의 후 **서버**에만 refresh/access 보관 | 사용자에게 “클라이언트 시크릿을 붙여넣으세요”보다 **연결됨 / 만료됨 / 다시 연결**이 안전하고 표준적이다. |
| **OAuth 앱 식별자 (Client ID 등)** | (선택) **자가 호스팅** 단일 사용자용 **설정** 화면에 입력 → **서버 저장**만 | `.env` 대신 UI로 넣게 하려면 값은 **절대 클라이언트 번들에만 두지 말고**, 서버 설정·암호화 저장소에 둔다. 저장 후 UI에는 **마스킹**만 표시한다. |
| **네이버** | 공식 API가 없다면 “계정 비밀번호” 입력 필드는 **지양** | HTML 미리보기·복사, 또는 (실험 시) 별도 경고와 함께 최소 정보 — 비밀번호 저장은 법·보안·약관 리스크가 큼. |

**안티패턴:** 브라우저 `localStorage`에 리프레시 토큰·클라이언트 시크릿만 평문 저장, 로그/스크린샷에 키 노출, “연결 테스트” 없이 저장만 하기.

**권장 UX:** 설정 탭에 **연결 상태**, **Google 연결 / 연결 해제**, **테스트 포스트(초안)**, 문서 링크(스코프·리다이렉트 URI 설정법)를 둔다.

## Open Questions

- 호스팅: 로컬 전용 vs Vercel/Fly 등 (OAuth 리다이렉트 URI에 영향).
- 인증: 단일 사용자(본인용) vs 멀티 테넌트.
- 이미지: Blogger API 첨부 전략(바이너리 업로드 vs 외부 URL).
- 설정 UI: OAuth만으로 충분한지, 아니면 **자가 호스팅용 Client ID/Secret 입력**까지 MVP에 넣을지.
- 인스타·Threads: **Buffer API** 연동 범위(채널 ID, 큐 vs 즉시, 스레드 최대 길이)와 실패 시 재시도.
- 뉴스레터: **메일리** 계정·API 키·수신동의·구독자 데이터는 메일리 측 정책을 따른다.
- 카드뉴스: **Gemini** 모델·이미지 생성 정책(금지 콘텐츠, 워터마크 등)과 **Google AI 이용약관**을 따른다.

## Success Criteria

- Blogger에 **제목·본문·태그**로 글이 실제 게시된다 (샌드박스 블로그로 검증).
- 동일 글에 대해 네이버용 **복사 가능 HTML** 및 발행 전 체크리스트가 UI에 있다.
- 동일 글에 대해 **인스타그램 캡션·Threads 스레드**가 생성되고, **Buffer API**로 큐에 적재되거나(또는 복사 fallback) 운영된다.
- (선택) 뉴스레터 HTML·제목이 **메일리** 편집·발송 흐름에 맞게 출력되거나 API로 연동된다.
- (선택) 카드뉴스용 이미지가 **Gemini API**로 생성되어보내기·Buffer 첨부까지 이어진다.
- OAuth 토큰이 저장소·로그에 평문으로 남지 않는다.

## 산출물 저장 (`_output/`)

- 모든 **채널별 생성물**(블로그 초안, 네이버 HTML, 소셜 문안, 뉴스레터 MD, 카드뉴스 이미지·로그 등)은 루트 **`_output/<매체>/`** 에 둔다.
- 매체 폴더 정의·파일명 규칙: **`_output/README.md`**.

## 발행 큐 워커 운영 (Vercel Cron)

- **트리거:** `vercel.json` 의 `crons` 항목 — `/api/cron/publish` 를 매 분(`* * * * *`) 호출.
- **인증:** Vercel 환경변수 `CRON_SECRET` 설정 시, Vercel Cron 이 `Authorization: Bearer ${CRON_SECRET}` 헤더를 자동 부착한다. 라우트는 이 헤더가 없거나 불일치면 401, `CRON_SECRET` 미설정이면 503 으로 안전 차단.
- **요금제 주의:**
  - **Hobby:** 크론 표현식이 무시되고 **하루 1회**만 실행됨. 분 단위 발행 필요하면 **Pro** 이상.
  - **Pro:** 모든 cron expression 허용. `* * * * *` 그대로 동작.
- **처리량:** 한 호출 = 한 배치(기본 10건, `?batch=N` 으로 1–50 조정). 한 잡 처리 시간은 외부 API(Buffer) 응답에 의존.
- **수동 트리거 (디버깅):**
  ```bash
  curl -X POST https://<host>/api/cron/publish \
    -H "Authorization: Bearer $CRON_SECRET"
  ```
- **로컬 개발:** `npm run dev` 후 동일한 curl 로 호출 가능. `.env.local` 에 `CRON_SECRET` 지정.
- **재시도 정책:** `requeueOrFail` 가 지수 backoff (1m → 5m → 25m → ... cap 6h) 로 `run_after` 갱신. `max_attempts` (기본 3) 도달 시 `failed`. `fatal` 핸들러 결과는 attempts 를 점프시켜 즉시 `failed`.

## 서브에이전트·웹앱 연동

- **Claude / Task 분기:** 코리아교육그룹 출판 마케팅 역할은 `.claude/agents/keg-*.md`에 정의한다. 의도→에이전트 표는 **`CLAUDE.md`** 의 *Subagent routing* 절.
- **웹앱:** 동일 `id`·키워드·`_output/` 하위 경로를 `src/lib/marketing/subagents.ts`의 `MARKETING_SUBAGENTS`로 노출한다. 편집기 상단 **에이전트 모드**·채널 탭·「추천 모드」는 `matchMarketingSubagentsByQuery(사용자 입력)` 등으로 매핑 가능.
- **동기화:** 새 역할을 추가할 때는 **에이전트 md + `subagents.ts` + `CLAUDE.md` 표 + `docs/subagents.md`** 를 한 세트로 갱신한다.

## Next Steps (구현 순서 제안)

1. `git init` + 기본 `.gitignore` (Node 기준이면 `node_modules`, `.env*`).
2. 스택 선택(예: Next.js + 서버 액션 또는 별도 API 라우트) — OAuth는 **서버 측**에서 토큰 교환.
3. Blogger: 최소 플로우 "로그인 → 블로그 선택 → 포스트 1건 발행".
4. 네이버: "보내기 패널"(HTML + 복사 버튼) + 정책 고지 문구.
5. 인스타·Threads: 카피 생성 + **Buffer API**로 `createPost`(또는 MVP는 복사 + 수동 Buffer 입력).
6. 뉴스레터: **HTML·제목** 산출 + (선택) [메일리 API](https://maily.so/app/guides/dev/dev-api) 발송·구독자 연동.
7. 카드뉴스: 프롬프트·`_template/card-news/` + **Gemini API** 이미지 생성 → **`_output/card-news/`** 저장·미리보기 → (선택) Buffer 미디어 업로드 플로우.
8. 큐 테이블(또는 SQLite)로 예약·재시도·발행 로그.

## What I noticed about how you think

- "Superpower 플러그인 확인"과 "브레인스토밍 스킬"을 같이 쓰자고 해서, **도구 규칙(검색·산출물)과 제품 전제를 한 번에** 잡으려는 방향이 좋음.
- 작업 범위를 **keg-book로 한정**한 것은 레포 비대화와 책임 분리에 유리함.
